# AGENTS.md

_Last updated: 2026-11-24_

`@workspace/shared` is a source-first TypeScript workspace library package for schemas, constants, and timezone/day helpers consumed by SparkyFitnessServer, SparkyFitnessFrontend, and SparkyFitnessMobile.

## Scope

- This package defines contracts and shared logic, not an app.
- Validate changes from consuming packages (server, frontend, mobile), not in isolation.
- Every schema change here potentially touches three packages.

## AI Coaches

`src/coaches/` holds what the server job and the web Preview both read: `signals.ts` (the fixed list of numbers a rule may use, ids and kinds only), `rules.ts` (rule and override schemas, at most 8 rules of 4 conditions), `catalog.ts` (`BUILTIN_COACHES`: key, tool categories, default rules) and `evaluate.ts` (pure `evaluateCoachRules`, `mergeBuiltinRules`, `slotPartOf`). No user-facing text lives here; each app words coaches, signals and rules in its own locale files. API contract: `schemas/api/Coaches.api.zod.ts` (also `readChatCoachMessage` for a chat row's coach details); tables: `CoachProfile`, `UserCoaches`, `CoachNudges` in `schemas/database/`. `dailyOutlook.ts` works out the morning verdict in code, `suggestions.ts` is what a message proposes. `utils/loggingStreak.ts` is the logging streak used by the coaches and the assistant's streak tool.

## Food Assistant State

`schemas/api/FoodAssistant.api.zod.ts` and `schemas/database/FoodAssistant.zod.ts` define lasting preferences, versioned tasks, unresolved ingredients and idempotent operation records. All state is owner-only; these additive contracts do not change existing chat clients.

## Structure

- Mealie ingredient imports: `utils/recipeImport.ts` preserves explicit compatible quantities, bounds unresolved matching batches to twenty rows, adapts normalized Mealie food search for recipe browsing, and merges suggestions without replacing confirmed mappings in web and mobile. The API contract remains in `schemas/api/RecipeImport.api.zod.ts`.

- `src/glucose/context.ts` - shared glucose context loading and timezone-aware day projection for web/mobile. Reads use the canonical API contracts; independent source failures retain successful layers. `src/constants/bloodGlucose.ts` defines display units and conversion, and `src/utils/measurementTimeline.ts` preserves timestamped readings and sensor gaps. `src/schemas/api/SleepEntries.api.zod.ts` derives serialized sleep responses from the database schema.

- Family diary copies: `schemas/api/FoodEntryCopy.api.zod.ts` defines reviewed/selected requests in both directions and recipient meal types. `foodEntryCopyFingerprint` remains byte-compatible with older copy-from clients; `copyFingerprintFor(version)` selects the contract for both clients and the server. New copy-to requests use `foodEntryCopyToUserFingerprint`, which also checks notes, meal identity, caffeine, water, and alcohol.

- Cooked weight (#3534): `utils/cookedWeight.ts` holds the weight units the "Weighed it cooked" switch is offered for (`COOKED_WEIGHT_UNITS`, `isCookedWeightUnit`), the batch yield (`cookedYieldFactor`, `entryYieldFactor` = `cooked_quantity / quantity`), the raw portion from the cooked weight eaten (`rawQuantityFromCooked`, rounded to 2 decimals so web and mobile agree) and `isValidCookedQuantity` for the server check. `food_entries.cooked_quantity` is only set on diary entries; the API contract for the last cooked entry of a food is `lastCookedFoodEntry*` in `schemas/api/FoodEntries.api.zod.ts`. Tested in `SparkyFitnessServer/tests/cookedWeight.test.ts`.

- Barcode search: `schemas/api/FoodLookup.api.zod.ts` and `BarcodeLookup.api.zod.ts` define normalized foods and source comparison results. `utils/barcodeNutrition.ts` supplies one comparison basis for web and mobile.

- `src/features/optionalFeatures.ts` - optional features (#3487), the one registry of features a person can turn on or off, separately on the website and in the mobile app (`FEATURE_PLATFORMS`: `web`, `mobile`): `OPTIONAL_FEATURES` (group, default, storage: `choices` = `user_preferences.feature_choices`, `cycleSettings` = `cycle_settings.enabled`; today `cycle`, `medications` and `labResults`), `ChoiceFeatureKey` (the keys stored in `feature_choices`, the only ones the `PATCH` takes), `isFeatureEnabled(key, platform, sources)` / `isFeatureExplicitlyOff` over `FeatureSources`, `isFeatureEnabledAnywhere` (on in at least one app, for answers about neither app's screens), `filterByFeature` for lists and `isShownByFeature` for one item, `FEATURE_CUSTOM_CATEGORIES` (custom measurement categories a feature owns: cycle's reproductive ones, and for `medications` the GLP-1 daily check-in categories from `GLP1_CHECKIN_CATEGORY_NAMES` in `src/medications/glp1.ts`, the names web and mobile find them by, never localized) with `hiddenFeatureCustomCategories` (those of features turned off on purpose) and `withoutHiddenCategories` (a category list less them), and the schemas: `platformFeatureChoicesSchema` (one platform's choices; pattern-checked keys, so a newer app's keys are kept; at most `MAX_FEATURE_CHOICES`), `featureChoicesSchema` (the stored `{ web, mobile }`) and the strict `featureChoicesPatchSchema` (one platform or both). The API contract is `src/schemas/api/FeatureChoices.api.zod.ts`. Data of a feature kept in other modules is tagged next to it: `GLUCOSE_CONTEXT_KIND_FEATURES` in `src/glucose/context.ts` (glucose chart layers; `medication` belongs to `medications`) and `CHAT_TOOL_CATEGORY_FEATURES` in `src/constants/chatToolCategories.ts` (the web chat's tool chips; only the chip hides, never the stored selection or the server's tools). Ids only; labels live in each app. Tested in `SparkyFitnessServer/tests/optionalFeatures.test.ts`.
- Nutrition label scan: `schemas/api/NutritionLabelScan.api.zod.ts` is the `POST /api/foods/scan-label` contract. The result schema turns missing, blank, negative or non-numeric model output into null rather than failing, so web parses it as is and mobile's `LabelScanResult` is its output type.

## Naming Convention

Calorie-link eligibility is shared by server, web and mobile: `isCalorieLinkWorkoutSource` allows app-logged and Hevy workouts. `isAppLoggedWorkoutSource` still identifies only app-logged workouts; do not use it to split a link's workout and health-recording sides.

- `X.api.zod.ts` = API request/response schema
- `X.zod.ts` = database table schema
- Export everything from `src/index.ts`; consuming packages import both types and values via `@workspace/shared`

## Cross-Package Contract Rules

- Chat display labels, outside-result cleanup, argument previews and approval result states are shared in `src/utils/chatTools.ts`. Server-owned tool titles and destructive approval summaries travel in `metadata.custom.outsideSource`; `SparkyFitnessServer/ai/chatApprovalSummary.ts` from the repo root reads targets under the user's context before approval is requested.

- Changes to `src/schemas/api/` usually affect server routes and both frontend/mobile API clients.
- Changes to `src/schemas/database/` require matching server migrations and RLS policies when changing the stored schema. CI regenerates the schema backup after merge; never hand-edit or regenerate it locally. Mirroring existing columns missing from a Zod schema does not require another migration.
- Timezone/day-string helpers prevent bugs; prefer them over `toISOString().split('T')[0]`.
- Verified commands (run from `shared/`): `pnpm run typecheck`, `pnpm run format:check`, `pnpm run format`, `pnpm run i18n:audit`, `pnpm run validate` (typecheck + i18n audit + format check). The package has no lint or tests of its own; behavior is covered by the consumers' test suites.
- Shared exports ids and data; apps own translation. `pnpm run i18n:audit` (`scripts/audit-user-facing-strings.mjs`) fails when a file gains more prose in `label`/`title`/`description`/`message`/`hint`/`summary`/`body`/`text` properties than `scripts/user-facing-strings.baseline.json` allows (the cycle, GLP-1, and body-region English catalogs are grandfathered). After moving text out, run it with `--update-baseline` to lower the allowance; use `// i18n-ignore` for literals that must stay.
- Formatting uses the same `.prettierrc` as the other packages, and lint-staged formats staged `shared/` files on commit.
- CI (`.github/workflows/ci-tests.yml`) runs `Shared Validate` and re-runs the frontend, mobile, and server jobs on any `shared/**` change.
- Test any shared change from the consumer packages (`pnpm run validate` in SparkyFitnessServer, SparkyFitnessFrontend, and SparkyFitnessMobile after modifying shared).
