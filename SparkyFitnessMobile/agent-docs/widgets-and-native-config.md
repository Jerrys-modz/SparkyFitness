# Widgets And Native Config: details

Longer notes for the "Widgets And Native Config" section of [`SparkyFitnessMobile/AGENTS.md`](../AGENTS.md). Each one has a one-line link there.

## Resizable Android widgets

- Android widgets can be resized (#2050): every provider XML has `resizeMode="horizontal|vertical"` and no `maxResize*`; `minWidth`/`minHeight`/`targetCell*` are unchanged, so a new widget still lands at 2x1 (calorie) or 2x2 (macro, water), and `minResize*` is 110x40 dp for calorie and water (a one-row water widget is allowed) and 110x110 for macro. Each widget draws one layout per step in `WidgetSizes.kt` (`SizeMode.Responsive` picked through `LocalSize.current`, never `Exact`; from Android 12L the launcher picks among the layouts already sent and a resize needs no redraw, though the receiver still gets the resize broadcast, while Glance 1.1.1 redraws on Android 12 and below): the classic composition where it fits, and every other step keeps its content, adding to it or moving the shortcuts as described below. A step's height is about its content's height at font scale 1.3, worked out in `WidgetSizes.kt` (a line is about 1.33 x its sp, Glance keeps the font padding); a one-row widget on a phone's landscape home screen (about 51 dp) is shorter than any layout and cuts it; the reference cells are Pixel portrait 2 columns 130 dp / 1 row 102 dp and HyperOS 2 columns 149 dp, 3 columns 241 dp, 1 row 75 dp, 2 rows 167 dp, 3 rows 260 dp. For the calorie and macro widgets wide means at least 230 dp (3 columns on HyperOS, 4 on a Pixel). Calorie: below 96 dp tall (a HyperOS 2x1) search and scan sit beside the bar instead of being cut off; wide adds the Diary (`sparkyfitnessmobile://diary`) and fasting (`sparkyfitnessmobile://fasting`, the `FastingDetail` linking entry in `App.tsx`) shortcuts; wide and at least 160 dp tall, Goal / Food / Burned fill the flexible space, so a short widget cuts the figures rather than the shortcuts. Goal is food + remaining, worked out in Kotlin (the Dashboard's figure; the snapshot's `goal`, which the iOS medium widget shows as Goal, leaves out the exercise calories the dynamic and percentage modes add back), and the figures are hidden for a snapshot without `food`/`burned` (one stored by an older app) or without a goal. Macro: the 2x2 keeps the classic layout (a HyperOS 2x2 at 167 dp still cuts its shortcut row, accepted); wide, each row shows grams against the goal through `widget_amount_of_goal` inside `widget_grams` (so the translated unit stays) and the four shortcuts move to a column of 34 dp buttons on the right, which fits a two-row widget (the rows sit 5 dp apart so Fat still shows at font scale 1.3 on a HyperOS 3x2); wide and at least 255 dp tall, the shortcuts go back under the rows, the kcal eaten (`widget_kcal_eaten`, the snapshot's `calories`, which is `calorieBalance.eaten`) show under the kcal left, and the bars and spacing grow. In every macro row the label takes the width the value leaves, so a long label is cut and the grams stay whole. Water: the classic layout needs 140 dp of height (`WATER_CLASSIC_HEIGHT`; a HyperOS 2x2 is 167 dp); narrow and shorter, as a one-row widget or a Pixel's landscape 2x2 is, the amount sits over the bar and smaller buttons, with a status under the amount from 98 dp tall (a Pixel's one-row widget is 102 dp) and in its place on a shorter row (a HyperOS 2x1, 75 dp); at least 300 dp wide (`WATER_WIDE`, 4 columns on HyperOS), the amount and bar sit on the left and − / + on the right, with the title and status line from 140 dp tall, the status in place of the bar below that. Narrower widgets keep the stacked layouts, because beside the buttons an amount such as "1,250 / 2,800 ml" is cut at 3 HyperOS columns (241 dp) and at a Pixel's 4 (276 dp). Glance drops a container's children past the tenth (the macro and water columns already have nine), so new elements join an existing row or column. Kotlin is not compiled by CI: compile the widget sources locally against Glance 1.1.1 before pushing.

## Workout Live Activity

- The workout Live Activity (Lock Screen + Dynamic Island elapsed/rest timers) uses `expo-widgets`, whose generated `ExpoWidgetsTarget` extension coexists with the `@bacons/apple-targets` `targets/widget/` target. `src/services/WorkoutLiveActivityLayout.tsx` is the `'widget'`-directive layout (self-contained; only `@expo/ui/swift-ui` imports; epoch-ms props, never `Date`s) and must only be imported from `src/services/workoutLiveActivity.ios.ts` — `createLiveActivity` runs at module scope and would drag iOS native modules into the Android bundle. The `.ios.ts` service subscribes to `activeWorkoutStore` (ops held until persist hydration + instance reconcile) and serializes all start/update/end calls; the OS ticks the timers from absolute timestamps, no polling — the app pushes an update only on a real state change. The Lock Screen banner shows a small header (app icon, workout name, elapsed), the exercise as headline with "Set 1 of 3" (or "Next: Set 2 of 3 (65 lbs × 12 reps)" while resting), then either the set's target in the user's unit with a check button, or the rest row of "-15s", a large countdown, "+15s" and "Skip". Those two subtitle lines are formatted in the service from the `setProgress`, `nextSet`, and `nextSetWithTarget` templates and passed as `subtitleText`; the widget body only displays that string. The target comes from `describeActiveSetAssumed`, so an empty set shows the same grayed-in values the live row does. The rest "-15s"/"+15s"/"Skip" and active-phase "Complete" buttons (iOS 17+; inert below 17) fire a `LiveActivityIntent` that runs in the app process and lands in the service via `addUserInteractionListener`, which dispatches to store actions; the button `target` strings are duplicated by hand between layout and service because the `'widget'` body cannot import them. A press after a force-quit is lost (the event fires before JS boots). The rest progress bar is an OS-ticked `ProgressView timerInterval`; the `bannerSmall` slot targets the watchOS Smart Stack/CarPlay and stays button-free. Live Activities get NO `widgets[]` entry in `app.config.ts` (that array is only for home/Lock Screen widgets).

## Medication reminder buttons on iOS

- Taken, Skip and Snooze on a medication reminder are handled natively so they work with the app closed. The buttons do not open the app, and iOS gives a background launch no reliable JavaScript runtime. `modules/background-water/ios/MedicationNotificationActions.swift` registers a `NotificationDelegate` with expo-notifications' `NotificationCenterManager` from an app delegate subscriber (`MedicationNotificationSubscriber`, listed in the module's `expo-module.config.json`), so it sees each response before the emitter module that forwards it to JavaScript. It reaches the server with the Keychain login `BackgroundWaterModule.setConfig` keeps for the Siri and Shortcuts actions, lists the day's entries, skips doses `isDoseLogged` (ported to Swift) already covers, creates the rest, and clears sibling delivered and scheduled reminders. Snooze copies the reminder's content into a new time-interval notification (no network). The Swift mirrors `utils/medications.ts` and `doesNotificationMatchAction`; keep them in step. The category ids, action ids and data keys must match `notifications.ts` and `medicationReminderService.ts`; the action ids are the literal strings `medication-taken`, `medication-skip` and `medication-snooze`.
- One owner per tap: `medication_entries` has no unique constraint on a dose, so the native handler claims a press (`notificationId|actionId` in UserDefaults, before any work) and `processMedicationNotificationResponse` skips a claimed one through `isNativeMedicationActionClaimed` (`services/medicationNativeBridge.ts`). It claims nothing, and JavaScript logs as before, when there is no stored login (Taken and Skip) or the data is not a reminder it understands. It never claims an Android press. A tap delivered twice is claimed once.
- JavaScript applies the outcome through a ledger the native side fills (`readMedicationActionResults`, applied by `applyNativeMedicationActionResults` at startup, on foreground return and on the `onMedicationActionResult` event): a snooze is recorded in the snoozed-reminder store, a fully logged press clears its pending and snoozed records and refreshes the medication caches, and doses whose write failed go onto the existing pending-actions queue, which replays them (with the ownership check) when the app opens. The Snooze length is a JavaScript preference, so it is pushed down with `setMedicationSnoozeMinutes` (startup and `MedicationReminderReconciler`); native uses 30 until then.
- Safety rules in the native handler: Taken and Skip are claimed only for a reminder whose `userId` equals the account JavaScript last pushed with `setMedicationActiveUser` (from `MedicationReminderReconciler`, cleared by `clearBackgroundWater` on sign-out), otherwise JavaScript handles it with its own ownership check; native writes run one at a time (`MedicationWriteQueue`) so two reminders for one dose cannot both see it unlogged; a failed list is an error that queues every dose, never an empty list; each press is written to the ledger before any network work (with every dose to do), so a press iOS cuts short is retried (the retry lists the day first, so written doses are not repeated); the ledger is JSON (UserDefaults cannot hold `NSNull`), results leave it only when JavaScript acknowledges them after storing them (`acknowledgeMedicationActionResults`), and a failed dose is the last thing trimmed when it overflows; a snooze that failed to schedule gives its claim back so the press can be retried. The queue is replayed by `retryPendingMedicationActions` right after a native failure is stored, on foreground return and when `expo-network` reports a connection again, not only at the next reconcile (which does not run on reconnect). Reminders are bound to the account and the server: each carries the `userId` of its medication and the `serverId` of the saved server it was scheduled for, and native claims Taken and Skip only when the user id matches the one JavaScript last pushed and the server id matches the one in the stored login (`BackgroundWaterConfig.serverId`). Switching to another saved server therefore hands the old server's reminders to JavaScript at once, with no window. Reminders or logins from a build before this have no server id and are always left to JavaScript. The JavaScript handler carries the reminder's `serverId` into the live press and the pending record too: a press made for another saved server (for example a restored copy with the same user and medication ids) is queued, and the replay keeps it until that server is active. The JavaScript handler also checks ownership before writing a press, on Android too (one extra `GET /api/v2/medications` per press); a press for another account is queued like a failed write and replayed when that account is signed in.
- Not covered by CI or Jest: the Swift and the `ExpoNotifications` pod dependency the module now declares (CI does not build iOS). They are checked only by `npx expo prebuild --clean`, a build, and testing on a real iPhone with the app force-quit: Taken, Skip and Snooze from the lock screen, a group reminder, no network (the dose should land in the queue and log on the next open), and a signed-out device (JavaScript should handle the press). Attach a screen recording of that run to the PR.

## Custom widget (iOS, Edit Widget pickers)

- One WidgetKit widget (`customWidget`, kind `customWidget`, iOS 17+ because it is an `AppIntentConfiguration`). There is no builder or saved layout in the app: the person adds "Custom widget", touches and holds it, taps Edit Widget and picks up to four numbers (any of the 16 metrics or None), a style, a color and large text. Each placed widget is configured on its own. The options are the `CustomWidgetIntent` parameters and the `CustomMetricOption` / `CustomStyleOption` / `CustomAccentOption` enums in `customWidget.swift`; their raw values are the shared metric, style and accent ids, and `__tests__/config/customWidgetIntent.test.ts` fails if a metric or style in `shared/src/utils/widgetLayout.ts` has no case. Adding a metric means: the shared list, `WIDGET_METRIC_LINK_PATHS`, `widgetMetricSnapshot.ts`, an enum case, `customMetricInfo`, and the `widget.custom.metric.*` string.
- Four slots fill a medium widget's 2x2 grid. A small widget shows the first two, a Lock Screen rectangle the first three, circular and inline the first one (`customFamilyMaxMetrics`, mirrored from `WIDGET_FAMILY_MAX_METRICS`). "Style: Automatic" uses the placed size's default (`customFamilyStyles`, mirrored from `WIDGET_FAMILY_STYLES`, first entry is the default); a style the size cannot draw falls back to it.
- Numbers: `useWidgetSync` writes the day's `WidgetDataSnapshot` (one `{ value, goal?, progress?, unit }` per `WidgetMetric`) as the JSON string `customWidgetData` for every metric, always on iOS. A metric with no value today is left out, never sent as zero; the widget draws `–`. Energy uses the unit token `energy` (kcal, converted with the snapshot's `energyUnit`). `fasting_elapsed` carries the fast's start in epoch seconds with unit `since`, and the widget runs the clock with `Text(date, style: .timer)`. Weight and water follow the account's units (`kg`/`lb`/`st_lb`, `ml`/`oz`/`liter`).
- Fetching only what is needed: because the widget (not the app) picks the numbers, the app cannot know which ones. The widget stamps `customWidgetActiveAt` (epoch seconds) in the app group each time iOS asks for a timeline, which only happens while one is placed (never for the gallery preview). `useCustomWidgetActive` reads it on mount and each time the app returns to the foreground; while it is recent (two days) `useWidgetExtras` fetches fasting, sleep, both heart rates and the logging streak, and `useWidgetSync` reloads the widget. Without a widget those queries stay off. The first time, a newly added widget shows dashes for those extras until the app is opened once.
- Steps and weight come from the day's check-in the Dashboard already loads, so they cost nothing.
- Decoding is lenient on purpose (metric and style names kept as strings): the widget extension and the app update independently, so a value from a newer app must be skipped, never crash.
- Taps: `WIDGET_METRIC_LINK_PATHS` (shared) says which screen each number opens, all screens that need no params. The app sends the table in the snapshot as `links` so Swift never repeats it, and every path must be registered in `App.tsx`'s linking config (`__tests__/config/widgetLinks.test.ts`). Medium and large widgets link each number with `Link`; small and Lock Screen widgets have one tap target (`widgetURL`, the first number's screen).
- Do not use `AppIntentRecommendation` to list presets in the gallery: Apple documents it as inactive on iOS and macOS (watchOS only).
- Not compiled in CI-less environments: after changing `customWidget.swift`, run `npx expo prebuild --clean`, build in Xcode, and check Edit Widget, the Lock Screen shapes and StandBy on a device. Changing the intent's parameters resets the configuration of widgets already placed.
